**3. Check-in rung selection**: reuses `RUNGS = [1,3,5,7,9,12,15,18]` from `placementLadder.js` verbatim (no new rung table). Server computes `startRungIndex` = the highest rung index whose unit is `<=` the child's current effective level (`measured_unit ?? placement_unit ?? 1`), then bounds the ladder walk to `[max(0, startRungIndex-2), min(RUNGS.length-1, startRungIndex+2)]` — a child never sees a rung outside their neighborhood, and the walk still uses the exact same 2-word/tiebreak pass rules as placement (2/2 advance, 0/2 finalize-at-last-passed, 1/2 single tiebreak word) with **no delta** — reusing `issueRung`'s adjudication logic parameterized by a `bounds` range rather than forking a second implementation of the same rules.

**4. Never-regress rule, precise mechanic**: check-in's `finalize()` computes `rawMeasured = RUNGS[rungIndex]` (the raw reading, which CAN be lower than the child's stored level — a bad day) then `appliedMeasured = Math.max(rawMeasured, storedMeasuredUnit)` before writing `child_profiles.measured_unit`/`placement_unit` (floored per plan, same as placement's existing floor logic) — the enforced floor and the child's session-generator experience never regress. `placement_completed_at` always bumps to "now" regardless of raw vs. applied (a check-in IS a fresh measurement event either way — this is what drives the 30-day eligibility clock). The **raw** `rawMeasured` (not the applied/floored value) is what's logged in `checkin_completed`'s `product_events` payload and is what the growth chart plots — a dip is real information for the parent, never enforced on the child, matching the mission's own framing verbatim.

**5. 30-day eligibility rule, evaluated client-side**: `daysSince(activeChild.placement_completed_at) >= 30`, using data already fetched by `useChildProfilesQuery` — no new round-trip needed just to show/hide the eligibility card. `placement_completed_at === null` (never placed, or "start at the beginning" chosen) → **not eligible** — check-in re-probes an existing measurement; a beginner-by-choice child has nothing to re-check (the Placement Report card shows their state as "started at the beginning" instead, see PORTAL section).

**6. Growth chart data contract**: `[{date: 'YYYY-MM-DD', measuredUnit: number, source: 'placement' | 'checkin'}]`, ascending by date, sourced from the new `historyMode` endpoint's read of `product_events` (`placement_completed`/`placement_retaken`/`checkin_completed`, each event's `payload.trueMeasuredUnit` or `payload.rawMeasured` respectively). Deliberately plots the **raw/true** measured value at each point (never the free-tier-floored `placement_unit`) — floor-vs-measured is a display-time annotation (the existing upsell banner logic), not a data-shape decision, consistent with the mission's framing that measured level and enforced floor are different concepts everywhere in this feature.

## SERVER — token/adjudication endpoints, rate limits, telemetry (allowlist+CHECK proof)

Extended `api/session-generator.js` with two new modes (same precedent as `placementMode`/`reviewOnly` — no new endpoint file):

- **`checkinMode`** (`handleCheckin`): reuses `api/_lib/placementLadder.js`'s `RUNGS`/`pickRungWords`/`signLadderState`/`verifyLadderState` verbatim. `placementLadder.js` itself gained one small, backward-compatible change: `signingKey`/`signLadderState`/`verifyLadderState` now take an optional `context` string (default `'placement-ladder-v1'`, byte-identical to every existing placement call that omits it) — check-in signs under `'checkin-ladder-v1'` instead, so a placement token and a check-in token are cryptographically distinct and can never be replayed into each other's branch (verified live, see VERIFICATION). `handleCheckin` computes `centerRung` from `measured_unit ?? placement_unit ?? 1` (`rungIndexForLevel`), bounds the walk to `[centerRung-2, centerRung+2]` (clamped to `[0, 7]`), and reuses placement's exact 2-word/tiebreak pass rules — `bounds` rides along in the signed state so a stateless round-trip still remembers the walk's own limits. `finalize()` implements the never-regress rule (DESIGN LOCK item 4): `appliedMeasured = Math.max(rawMeasured, priorMeasuredUnit)` is what's written to `child_profiles`; `rawMeasured` (which can be lower) is what's logged to `product_events` for the growth line. Fixed one real boundary bug found before shipping (not after): `finalize(rungIndex)` can receive `rungIndex = bounds[0]-1` when a child fails even the lowest rung in their own tested neighborhood — the original `rungIndex >= 0 ? RUNGS[rungIndex] : ...` fallback would have read `RUNGS` at an index OUTSIDE the tested range (reporting a unit never actually verified this check-in); fixed to check `rungIndex >= bounds[0]` instead, flooring at the tested range's own bottom.
- **`historyMode`** (`handleHistory`): the one read path into `product_events` (still service-role-only/no-client-RLS, unchanged invariant). Ownership-verified via the same `fetchChildContext` every other mode uses, queries `placement_completed`/`placement_retaken`/`checkin_completed` ordered by `created_at`, and projects out only `{date, measuredUnit, source}` — never raw rows, never other event types.
- **Rate limits**: unchanged — both new modes ride the existing `session-generator` limiter (`requireAuthAndRateLimit(..., 10, 1)`, 10/min per authenticated user), same as every other mode. This surfaced directly during idor-proof extension (see VERIFICATION) — a debug session confirmed a real 429 mid-ladder when too many session-generator calls landed on one token within a minute, not a logic bug; the extended idor-proof checks were restructured to spend user B's rate-limit budget on the "drive a real check-in to completion" positive-twin flow rather than user A's (already spent on the forgery checks).
- **Telemetry — allowlist+CHECK proof**: `checkin_started`/`checkin_completed` are logged via the same internal `logProductEvent` helper `placement_started`/`completed`/`skipped`/`retaken` already use — server-side only, never posted by the client through `/api/track`, so (per precedent, documented explicitly in DESIGN LOCK) `api/track.js`'s `EVENT_SCHEMAS` allowlist was deliberately NOT touched; only migration 0036's CHECK constraint was extended. ## TRAPS — reusable lessons

1. **`waitForResponse` must be armed before its triggering action, not after** — arming it right after a click that already fired (and whose response may have already resolved by the time your assertions confirm the UI updated) deadlocks forever waiting for a network call that will never come again. Arm it immediately before the click/action that causes the request, every time, for any multi-step server-adjudicated flow (ladders, wizards, anything stateless-round-tripped).
2. **A shared signed-token helper used by two different ladder-style flows should sign under different context strings per flow**, not just rely on childId/expiry checks to keep them separate — costs nothing (same HMAC derivation, one more string parameter) and closes an entire class of cross-mode replay confusion for free. Retrofittable without breaking existing callers if the context parameter defaults to the original value.
3. **Rate limits are shared per authenticated user across ALL modes of a multi-mode endpoint** (`session-generator`'s 10/min covers `placementMode`/`reviewOnly`/`checkinMode`/`historyMode`/plain generation alike) — a verification script that runs many forgery/negative checks against one token before also trying to drive a REAL multi-step flow to completion on that SAME token can burn its own budget and produce a false-negative failure that looks like a logic bug. Spend a second test identity's fresh budget for anything that needs several consecutive real round-trips, or spread calls with delays.
4. **`finalize(rungIndex)` in a bounded-ladder walk needs its "nothing passed" sentinel checked against the walk's own lower bound, not literally 0/negative** — a bounded sub-range ladder (unlike the full 0-indexed placement ladder) can have `lastPassedRungIndex` start at a POSITIVE number one below its own bounds[0], and a naive `rungIndex >= 0` fallback check will read `RUNGS` at an index outside what was actually tested, silently reporting a unit that was never verified this round.
5. **`child_profiles`'s table-level `REVOKE UPDATE` (migration 0033) only blocks `authenticated`/`anon`, never `service_role`** — test fixtures can (and should) seed these otherwise-client-unwritable columns directly via the admin/service-role client rather than trying to route seed data through a slower UI flow or a workaround endpoint.
6. **Reusing a production component unmodified is itself a compliance guarantee, not just a DRY nicety** — `CheckInScreen` importing `PlacementProbe.jsx` as-is (rather than forking a near-copy) means §5a's measurement exception ships correct by construction; a fork would need its own from-scratch tone-parity proof and could silently drift from placement's over time.
7. **Vite dev-mode's native-ESM live-binding throws hard on a missing named export; `vite build`'s Rollup bundling silently tolerates the exact same missing export.** A stale `import { x } from './y'` where `y` no longer exports `x` (e.g. after refactoring `x` out into its own file) will pass `npm run build` clean, pass every preview/production walk clean, and still crash the ENTIRE app the moment anyone runs the local Playwright suite or `npm run dev` — because only the dev-mode module graph enforces the binding strictly. **A widespread, uniform-looking "everything times out" test failure pattern is not proof of an environmental cause** (resource pressure, rate limits) just because the symptom LOOKS environmental (timeouts, no assertion mismatches) — capture actual browser console/page errors directly (a five-line Playwright script: `page.on('pageerror', ...)`, navigate, read the message) before concluding "it's the environment, not my diff." This run initially misdiagnosed exactly this failure as pure memory pressure for over an hour of wall-clock retries before the console-capture step revealed the real cause in under a minute.
8. **An unused/dead import is not harmless just because nothing references the imported binding** — `DashboardTab.jsx`'s `import StarCheckInCard, { isCheckinEligible } from './StarCheckInCard'` never called `isCheckinEligible` anywhere in the file, but Vite's ESM import validation happens at module-load time regardless of whether the binding is ever used — dead imports need to be cleaned up immediately when a refactor moves what they used to point at, not left "since it's unused anyway."

## NOTES FOR PACKAGES D/E — what admin + quick-wins should reuse

- **`checkinEligibility.js` and `masteryCalibration.js` are the model for any future client-side gating rule**: zero imports, plain-Node-testable, imported by whichever React component needs the gate. If a future package needs a similar "is X eligible for Y" rule, follow this exact shape rather than inlining the logic in a component.
- **The `historyMode`-style "ownership-verified minimal-projection read endpoint into an otherwise service-role-only table" pattern is reusable for any future admin-facing report** that needs to surface `product_events`/`security_events` data without opening client RLS on those tables — extend `session-generator.js` with another mode (or, if it grows too many unrelated modes, this is the natural point to split telemetry-reads into their own endpoint file) rather than granting a new SELECT policy.
- **`RUNGS`/`pickRungWords`/the signed-ladder-token pattern in `api/_lib/placementLadder.js` is now used by two features** (placement, check-in) with per-flow signing contexts — a third bounded-probe feature (if one is ever needed) should extend this same file with its own context string rather than forking the ladder logic again.
- **The never-regress rule's mechanic** (`appliedMeasured = Math.max(raw, prior)` written to the enforced/floor-driving columns; the raw reading logged separately for historical/informational display) **is a reusable pattern for any future "recurring measurement that must never make the product worse for the user"** — Package D/E should reach for this shape rather than re-deriving it if a similar recurring-measurement feature comes up.
